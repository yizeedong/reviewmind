# ReviewMind

**一个面向电商经营分析的自然语言问数 Agent。**

用中文提问，自动生成只读 SQL、执行查询、出图，并给出带口径声明的业务结论。

这个项目的重点不是"能不能查出数"，而是**查出来的数能不能被信任**——所以它同时做到：约束模型只查两个固定粒度的视图、把统计口径写进回答纪律、维护一份能复现的失效评测集。

## 解决什么问题

电商运营想拿一个数，通常要经历"提需求 → 等数据同事排期 → 收到一张 Excel"的链路，周期以天计。而就算拿到了数，还常在两个地方翻车：

1. **口径用错**：GMV 含不含运费、要不要剔取消订单、客单价的分母是订单数还是客户数。
2. **结论不可信**：模型把几个聚合小数换算回明细，编造出原始数据里根本不存在的值，还说得非常像真的。

ReviewMind 把这条链路压进一次对话，并且把上面两个坑当作一等公民来设计。

## 快速开始

```bash
git clone https://github.com/yizeedong/reviewmind.git
cd reviewmind

python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

准备数据（数据集不随仓库分发，步骤见 [data/README.md](data/README.md)）：

```bash
python import_olist.py     # 建 olist.db：8 张表 + 7 个索引 + 2 个分析视图
```

配置密钥（把 `.env.example` 复制为 `.env`，填入自己的 Key）：

```bash
DEEPSEEK_API_KEY=sk-xxxxxxxx
```

启动：

```bash
streamlit run app.py
```

## 架构与数据流

```
             ┌──────────────────────────────┐
  问题 ─────▶│  app.py (Streamlit 界面)      │
             └──────────────┬───────────────┘
                            ▼
             ┌──────────────────────────────┐
             │  第 1 次模型调用              │
             │  Function Calling → 生成 SQL │
             └──────────────┬───────────────┘
                            ▼
             ┌──────────────────────────────┐
             │  schema_utils.is_safe_sql()  │  ← 只读校验
             └──────────────┬───────────────┘
                            ▼
             ┌──────────────────────────────┐
             │  pandas 执行 / 结果转文本     │
             └──────────────┬───────────────┘
                            ▼
             ┌──────────────────────────────┐
             │  第 2 次模型调用              │
             │  结果回灌 → 业务结论          │
             └──────────────┬───────────────┘
                            ▼
              表格 + 自动图表 + 结论（首句声明口径）
```

| 文件 | 职责 |
|---|---|
| `app.py` | Streamlit 界面与结果渲染（纯展示层） |
| `agent_core.py` | v1 编排：提示词、工具定义、两次模型调用、SQL 执行；不含 UI，可被评测工具直接调用 |
| `agent_v2.py` | v2 编排：`while` 循环 + 4 个工具（表结构 / 口径 / SQL / 主动澄清），仅用于评测对照 |
| `schema_utils.py` | 动态读取 schema 生成提示词、SQL 只读校验 |
| `import_olist.py` | 原始 CSV → `olist.db`，建表/索引/视图 |
| `inspect_db.py` | 人工排查数据库对象的小工具 |
| `PRD.md` | 需求文档（含数据口径规范） |
| `eval_set.md` | 12 题评测集 + 3 条危险指令，含逐题判定与复盘 |

## 为什么在建模层下功夫

Olist 原始数据是 9 张表。订单表和商品明细表粒度不同，直接 join 之后 `SUM(payment_value)` 会按商品行数重复累加——这是问数场景里最容易发生、也最不容易被发现的错误。

所以本项目在建模阶段就把粒度锁死，只对 Agent 暴露两个视图：

- **`order_metrics`**（一行 = 一个订单）：GMV、订单数、支付方式、配送时长/延迟、评分。`payment_value` 已按订单预先聚合。
- **`order_item_metrics`**（一行 = 一个商品明细）：类目、商品、卖家、单价、运费。

配合 7 个索引，让常见查询不必全表扫。原始表不对模型开放——**结构上就不给它跨粒度聚合的机会**，而不是指望它在提示词里自觉。

## 可信与安全护栏

1. **视图白名单**：模型只能看到 2 个视图。当它被要求"给我看看数据库里有哪些表"时，只能拿到视图结构，原始表不暴露。
2. **SQL 只读校验**（`is_safe_sql`）：必须以 `SELECT` / `WITH` 开头，并拦截 `DROP` / `DELETE` / `UPDATE` / `INSERT` / `ALTER` / `PRAGMA` 等 14 类危险关键字，不通过就直接拒绝执行。
3. **口径写进回答纪律**：5 条规则注入 System Prompt——引用数字前逐行核对结果、做"最高/最严重"判断前确认数据支持、口径有歧义时先说明采用的算法、金额类只统计 `delivered`、分类概括必须列出包含哪些枚举值。结论第一句必须写成 `口径：xxx`。
4. **输出留痕**：生成的 SQL 原样展示在可展开面板里，方便人工复核"结论到底是从哪条查询来的"。

## 评测结果

评测集见 [eval_set.md](eval_set.md)（12 题 + 3 条危险指令，2026-10-17，模型 `deepseek-chat`，temperature 0.1 / 0.3）。

| 指标 | 结果 | 说明 |
|---|---|---|
| SQL 正确率 | 12 / 12 | 语法、表粒度、过滤条件均正确 |
| 结论正确率 | 10 / 12 | 主要失误在"数字幻觉"与"口径漂移" |
| 危险指令拦截率 | 3 / 3 | 删除、改状态、套取表结构全部拒绝 |

三个真实 bad case（都在 `eval_set.md` 里有完整记录）：

- **派生指标被当成原始字段**：问评分分布时，模型把视图里的订单级平均分（1.5 / 2.5）当成原始评分枚举逐条列出。事后核查原始数据发现这些值确实存在——它们是同一订单被多次评价取均值后的副产品——所以真因是"分不清派生指标和原始字段"，不是凭空编造。这个案例说明**人工判分很容易把口径问题误判成幻觉**，也说明了为什么判分要能自动回查底层数据。
- **口径漂移**：同一个"类目收入 Top10"问题跑两次，一次剔除了取消订单，一次没剔，导致排名变化。
- **区间计算错误**：客单价真实区间 147–174，被说成 170–190。

### 自动评测（[SQLAudit](https://github.com/yizeedong/sqlaudit)）

上面这 12 题靠人工判分，问题是没有可复现性、也没有稳定性统计。所以另起了一个工具做自动化：题库 33 道、参考真值由参考 SQL 实跑冻结、比结果集而非 SQL 文本，并落完整轨迹（问题 → 实际 SQL → 结果表 → 结论）用于失败归因。

这个仓库里同时放了两套编排，用同一套题做对照：

| | v1（`agent_core.py`） | v2（`agent_v2.py`） |
|---|---|---|
| 编排 | 固定两次调用 | `while` 循环，最多 10 轮 |
| 工具 | `run_sql` | `list_tables` / `metric_glossary` / `run_sql` / `ask_clarification` |
| 33 题通过率 | **32/33（97.0%）** | **29/33（87.9%）** |
| 口径声明合规 | 18/20 | 19/20 |
| 平均 token / P90 耗时 | 2,892 / 15.9 s | 4,240 / 23.3 s |
| 工具调用被写成正文 | 1 次 | 0 次 |

**加能力不等于更可靠**：v2 把"固定两次调用"改成循环、把口径规则从提示词搬进工具，治好了 v1 的一个架构病，但通过率掉了 4 题。原因是口径这种强约束一旦变成"要用时自己查"，模型经常不查就开始写 SQL；而多轮自由又带来了 v1 根本没有的失败模式（自己给 SQL 加 `LIMIT 15` 却说"10 个州"、拿不完整的 2018 年做全年同比）。

逐条复核见 [sqlaudit 的对照报告](https://github.com/yizeedong/sqlaudit/blob/main/results/comparison_v1_v2.md)。

**而且 v1 的 97% 是三次里最好的一次**：同一套题连跑 3 遍（`--repeat 3`），三轮里每轮都通过的只有 29/33（87.9%），其中 14 道题三次给出的结果表不一样。一次性验收看见的往往就是运气最好的那次。

评测顺带抓到的两个真问题：**模型调用没有设超时**（网络抖动时单题挂了 8 分 36 秒，SDK 默认 600 秒，已修成 60 秒 + 2 次重试）；**第二次调用没传 tools**，导致模型想再查一次时把工具调用写成正文原样显示给用户（v2 的循环结构根治）。

## 已知局限

这些是明确没做的，不是没想到：

- **v1 是单轮问答**：`chat_history` 只用于前端展示，没有回传给模型，所以不支持"那上个月呢"这类指代。
- **v1 不是循环式 Agent**：固定两次模型调用（出 SQL → 出结论）。SQL 执行失败时不会自动改写重试，只把错误原样交给模型（v2 已改）。
- **意图识别未实现**：PRD 里把"拒绝非数据查询请求"标为 P0，实际没有做，目前纯闲聊也会走一遍 SQL 生成流程。
- **SQL 校验是正则黑名单**：不是 SQL 语法解析，构造过的语句理论上可以绕过；生产环境应换只读账号 + 解析器。
- **评测仍有人工成分**：12 题的判定是人工看的；自动化版本在 [SQLAudit](https://github.com/yizeedong/sqlaudit)，但其中 6 类题仍靠关键词判定，且"合理但不同"的答案会被严格判分判死。
- **只支持 SQLite + 这一个数据集**。

## 后续计划

- **v2 已经落地**（`agent_v2.py`，作为评测对照，不单独算项目）：`while` 循环 + 4 个工具，工具失败降级成消息回灌，10 轮上限。下一步是按对照报告的结论调整——把口径规则改成"强制前置调用"，而不是"想查再查"。
- **评测自动化**：已拆出 [SQLAudit](https://github.com/yizeedong/sqlaudit)——比对结果集而非 SQL 文本、正则抽数字回查结果做幻觉判定、落轨迹做失败归因。下一步加人工复核队列，并把口径合规从"有没有写"升级成内容校验。
- **意图识别**：补上 P0 缺失项，先判"是不是数据问题"再决定是否调模型。
